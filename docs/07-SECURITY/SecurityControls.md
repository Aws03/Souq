# Souq: security control catalog

> One row per control that exists (or is missing) in this repository. Narrative and rationale: [Security.md](Security.md) · identity and permissions: [AuthenticationAndAuthorization.md](AuthenticationAndAuthorization.md) · isolation design: [MultiTenancy.md](../02-ARCHITECTURE/MultiTenancy.md).

## How to read this page

- **Status** is what the code does **today**:
  - **CURRENT** — implemented and (unless stated) covered by a test;
  - **PARTIAL** — implemented for part of the surface, or without the guarantee the name suggests. The gap is stated in the same row;
  - **PLANNED** — scheduled in [ProductRoadmap.md](../12-ROADMAP/ProductRoadmap.md) and **not implemented**. Items that are only an option, or were consciously postponed, are labelled FUTURE or DEFERRED instead.
- **Implementation** names stable paths and symbols, never line numbers.
- **Tests** names the test class that would fail if the control were removed. Test methods are Arabic; they are described in English here.
- A control's absence is as important as its presence. Section 12 collects every gap with a suggested remedy; each gap also appears in the row that owns it.

## 4. IDOR prevention

Two layers answer "can I ask for this id?". **Tenancy** removes rows that belong to another store before the use case sees them (section 3). **Ownership** removes rows that belong to another customer, inside the use case, with a 404.

### Client-side session controls

These are not IDOR controls — the server authorizes every request regardless — but they decide what one browser session can see or lose, so they sit beside them.

| ID | Control | Threat | Implementation | Tests | Status |
|---|---|---|---|---|---|
| SEC-SESS-01 | A refresh that fails for a **transient** reason does not end the session | A customer signed out mid-journey — possibly mid-checkout — by a rate limit or a brief server fault they did not cause | `refreshSession` distinguishes three outcomes: a user, a **confirmed** expiry (401/403 — the stale access token is dropped), and **unknown** (429, 5xx, network). Only a confirmed expiry raises `SESSION_EXPIRED`; an unknown outcome leaves the session alone, and `AuthProvider` retries once after 1.5s before falling back to guest | `client.test.js` (429, 503 and a dropped network are each `unknown`; 401 is `expired`; the event fires only on 401), plus the Phase 16 browser journey that found it | **CURRENT (Phase 16).** Found by browser validation, not by reading: the journey failed intermittently and the auth trace ended `register→200  refresh→429`. The visitor had made ten guest page loads, each firing a refresh that could only ever return 401, exhausting the per-IP bucket |
| SEC-SESS-02 | The browser's query cache is emptied whenever the signed-in identity changes | One customer's orders, profile or addresses rendered for the next person to sign in on the same device | Signing out and in does not reload the page, so the in-memory cache would otherwise survive it. `QueryProvider` calls `resetQueries()` on every change of user id — `clear()` was tried first and is **not** sufficient: it empties the cache but leaves a mounted screen holding the data it already has, and it never refetches | `QueryProvider.test.jsx` (identity change, sign-out, and no reset on an ordinary re-render) | CURRENT (Phase 16). The server authorizes every request regardless; this control is about what is painted before the server is asked at all |

| SEC-HTTP-07 | An unknown host gets nothing | Host-header attacks, tenant guessing | `TenantResolutionMiddleware` answers `404 StoreNotFound` for `/api` and `/uploads` before any logic; `AllowedHosts` stays `*` because the store map is the real check | `TenantResolutionMiddlewareTests`, `TenantResolutionTests` | CURRENT |
| SEC-HTTP-08 | One error contract, no internals | Fingerprinting through error shapes | RFC 7807 ProblemDetails with a stable `code` and `traceId` for every error, including framework 401/403/404/405 (`UseStatusCodePages`) | `ErrorContractTests`, `GlobalExceptionHandlerTests` | CURRENT ([ADR-0017](../11-ADR/0017-error-contract.md)) |
| SEC-HTTP-09 | Request bodies are bounded | Memory exhaustion | Per-endpoint `[RequestSizeLimit]` on uploads and, since M15, on the payment webhook (64 KB); nginx `client_max_body_size 55m` | — | PARTIAL: still no explicit global limit, so the framework default applies to JSON endpoints. The webhook was the sharp case and is closed: it is anonymous by necessity, unrate-limited, and read the whole body into a string *before* the signature was judged — after which the router also loaded the store account, AES-GCM-decrypted its key and computed an HMAC over whatever arrived. Real Stripe events are orders of magnitude under the new ceiling |

---

| SEC-HTTP-10 | API responses are never cached (M15) | A personal response left in a shared browser's disk cache | `SecurityHeadersMiddleware` sets `Cache-Control: no-store` on every API response as a **default, not a mandate** — an endpoint that sets the header keeps its own, the same rule the CSP in that middleware follows. `/api/storefront/config` is the one that does, deliberately: public display data with an ETag so the browser can revalidate into a 304 | `SecurityHeadersTests` asserts both halves — the default on paths that say nothing, and that the config endpoint keeps `no-cache` with its ETag | CURRENT. The response that made this worth doing is `GET /api/account/export`, which returns the customer's whole profile, addresses, orders and reviews as a download and previously carried no cache directive at all |
| SEC-HTTP-11 | The rate limit is keyed on the store, not on how its host was typed (M15) | Unlimited credential stuffing, reset-mail flooding and coupon guessing | `RateLimitPartition` and `TenantResolutionMiddleware` both build the key through one `RequestHost.Canonical` | `AuthSessionTests` (upper, mixed and trailing-dot variants must share one bucket) | CURRENT. **This was an open bypass until M15 and was proven exploitable on a running stack**: the limiter keyed on `Request.Host.Host` as it arrived while tenant resolution lower-cased it, so one store had a fresh bucket per capitalisation — ten logins then 429, then fourteen more varying only the case, all accepted. It needed no proxy bypass and no forged header, and it worked straight through nginx, which forwards `$http_host` verbatim |

## 12. Gaps and risks

Ordered roughly by exposure. "Remedy" is a suggestion, not a commitment.

| # | Gap | Why it matters | Suggested remedy |
|---|---|---|---|
| ~~G-01~~ | **Closed as a file, open as a setting.** [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) runs the suites, the frontend lint, type-check, tests and build, `dotnet list package --vulnerable`, a blocking `npm audit` over shipped dependencies, and a secret scan | — | **Remaining:** branch protection on `main` must be switched on in GitHub, or a red run can still be merged. That is a repository setting only the owner can change (TD-31) |
| G-02 | **No HTTPS in the shipped stack**, and the SPA's CSP is not yet enforced (SEC-HTTP-03, SEC-HTTP-04) | A deployment that forgets TLS silently breaks the `Secure` cookies and exposes tokens; a report-only CSP observes but does not block | Terminate TLS at the edge; confirm the SPA CSP in a browser (storefront **and** checkout) and rename the header to `Content-Security-Policy` |
| ~~G-03~~ | **Closed.** `frontend/nginx.conf` now logs a `souq_safe` format: the query string is stripped, `/track/…` paths are redacted, and `Referer` is never written. Verified against the running container | **Note for the deployment:** an outer load balancer or CDN in front of this stack keeps its own access log, and that one is not covered here — apply the same rule where TLS terminates |
| G-04 | **Logout does not end the access token** (SEC-AUTHN-11) | "Log out" on a shared machine leaves a working token for up to 15 minutes if it was captured | Rotate the security stamp on logout (it already invalidates everything) or accept it explicitly and document the window |
| G-05 | **Audit coverage is partial** (SEC-AUTHZ-10) | Order status changes, coupons, shipping methods and product create/update leave no `AuditEntries` row, so a store cannot reconstruct who changed a price or a coupon | Add `IAuditable` to those commands; the behavior does the rest |
| G-06 | **Lockout enables enumeration and targeted denial of service** (SEC-AUTHN-03) | An attacker can confirm an address exists and keep a specific customer locked out | Return the same code for locked and wrong-credential cases, and consider an IP-scoped delay instead of an account-scoped lock |
| G-07 | **Email verification is never required** (SEC-AUTHN-15) | Orders and notifications can be tied to an address nobody proved they own | Make it a store setting enforced at checkout, as Phase 3 intended, or state in the roadmap that it is out of scope |
| G-08 | **Rate limits are in-process and cover a narrow surface** (SEC-AUTHN-14) | Limits multiply by instance count; checkout, review posting and the webhook are unlimited | Move the limiter to a shared store when the app scales out; add limits to checkout and reviews |
| G-09 | **Deployments still connect to SQL Server as `sa`** (`docker-compose.yml`) — Phase 0 finding B10. The mechanism exists and was measured: `scripts/sql/least-privilege-logins.sql`, `ConnectionStrings:Migrations`, `scripts/verify-least-privilege.sh` ([DatabasePrivileges.md](DatabasePrivileges.md)) | One SQL injection or one leaked connection string owns the whole instance, not just the application's data | Apply the runtime and migration logins in the real deployment (R-12 in [ReleaseReadiness.md](../09-OPERATIONS/ReleaseReadiness.md)) |
| G-10 | **Migrations run at application startup** | A bad migration takes the API down and can race between instances | Move migrations to a deployment step with a migration bundle (PLANNED, Phase 23) |
| G-11 | **Secret rotation is manual with no re-wrap** (SEC-CFG-07) | The old key must live indefinitely, and removing it makes stores' payments fail with a 503 | Add a command that re-encrypts stored ciphertexts with the active key |
| G-12 | **Orphan uploads are never deleted** (SEC-UP-06) | Storage grows forever and removed images stay reachable by URL | Add a delete to `IFileStorage` and a sweep of unreferenced keys |
| G-13 | **Single-instance assumptions** — the stamp cache (30 s), the tenant directory cache (60 s) and the rate limiter are per process | Revocation and store suspension lag; limits weaken; correctness is unaffected | Shared cache or pub/sub invalidation before running more than one instance ([ADR-0022](../11-ADR/0022-tenancy-enforcement.md), [ADR-0023](../11-ADR/0023-sessions-and-credentials.md)) |
| G-14 | **No absolute refresh lifetime** and no "log out everywhere" | A stolen refresh token used regularly never expires | Add a family start timestamp and a maximum age (PLANNED, Phase 20 review). Global logout is **DEFERRED**: the Phase 16 account page shipped without it and no endpoint exists |
| G-15 | **No MFA, no SSO** | High-value platform and store-admin accounts rest on one password | Adopt an external IdP behind the existing claims contract when a client needs it ([ADR-0010](../11-ADR/0010-authentication-authorization.md) revisit condition) |
| G-16 | **Minor-unit risk for three-decimal currencies (P-05)** (SEC-PAY-12) | A wrong multiplier charges a tenth of the price | Confirm the behaviour on the real Stripe account before enabling live payments in such a currency |
| G-17 | **The API port is published next to nginx and the trusted proxy range is wide** (SEC-HTTP-06) | Rate limiting and audit addresses can be influenced by a client that bypasses the proxy | Remove the published port in production; trust only the proxy's address |
| ~~G-18~~ | **Closed.** The frontend runs Vite 8, Vitest 5 and `@vitejs/plugin-react` 6 after a measured upgrade (TD-41) that changed no application code and forced Node 20 → 22 in CI and the image | — | — |
| G-19 | **The SPA asks `/api/auth/refresh` on every page load, including for visitors who have never signed in.** Ten guest page views are ten calls that can only return 401, and they share the per-IP `Refresh` bucket (30/60s) | A customer behind a shared address (an office, a mobile carrier) can be refused a refresh they genuinely need, and on a busy shared address this is not rare. The client no longer signs them out for it (SEC-SESS-01), but the call is still wasted and the bucket still fills | The refresh cookie is `HttpOnly`, so the browser cannot know whether one exists. Either set a readable, non-secret marker cookie beside it and skip the call when it is absent, or exempt the *unauthenticated* refresh from the bucket. Needs a decision on the auth contract, so it is recorded rather than patched in a storefront phase |
| G-20 | **Registration discloses that an address exists** (`409 EmailTaken`) | Account enumeration on the registration route | Accept the trade-off explicitly, or answer generically and send a "you already have an account" email |
| G-21 | **No SQL Server Row-Level Security** | Isolation depends entirely on application-level filters and the write guard | Optional defence in depth: an optional item in the Phase 20 security review scope (**PLANNED**, optional) |
