# كيف تُفكّر كمهندس برمجيات؟
## إطار عمل كامل لبناء مشروع من الصفر — مع تطبيق عملي على متجر إلكتروني

> **الفكرة المركزية:** المبرمج يكتب كوداً يعمل. المهندس يبني *نظاماً* يستمر في العمل ويتطوّر ويُصان لسنوات، حتى بعد أن يتغيّر فريقه وتتغيّر متطلباته. الفرق ليس في معرفة لغة برمجة، بل في **طريقة التفكير قبل وأثناء وبعد الكود**.

---

## الجزء صفر: العقلية الهندسية (الأساس قبل كل شيء)

قبل أي خطوة تقنية، يجب أن تتبنّى ثلاث عقليات أساسية. هذه تجيب مباشرة عن سؤاليك رقم 13 و14.

### 1. عقلية "الصندوق الأسود ثم الصندوق الشفاف" (Top-Down Thinking)

المهندس المبتدئ يبدأ من التفاصيل: "أي جدول أنشئ أولاً؟ أي ملف؟". المهندس المحترف يبدأ من الأعلى ويُنزل تدريجياً:

```
النظام ككل (متجر إلكتروني)
   ↓
ما الذي يفعله النظام؟ (يبيع منتجات، يدير طلبات، يحصّل أموالاً)
   ↓
ما المجالات الكبرى؟ (Catalog, Cart, Orders, Payments, Users)
   ↓
ما الذي يحدث داخل كل مجال؟ (إضافة منتج للسلة، إتمام الدفع...)
   ↓
ما الكيانات والبيانات والقواعد؟
   ↓
الكود (آخر خطوة، وليست الأولى)
```

**القاعدة الذهبية:** لا تكتب أي كود حتى تستطيع أن تشرح النظام بالكامل لشخص غير تقني في 3 دقائق.

### 2. عقلية "الفصل بين القرار والتفصيل" (Separating Policy from Detail)

في كل لحظة اسأل نفسك: *هل هذا قرار جوهري (Policy) أم مجرد تفصيل تقني (Detail)؟*

| قرار جوهري (يبقى ثابتاً) | تفصيل تقني (قابل للتغيير) |
|---|---|
| "العميل لا يستطيع شراء منتج كمّيته صفر" | هل نستخدم SQL Server أم PostgreSQL |
| "الطلب يمرّ بحالات: Pending → Paid → Shipped" | هل الواجهة React أم Angular |
| "السعر يُحسب مع الضريبة عند إتمام الطلب" | هل نستخدم REST أم GraphQL |

المهندس المحترف **يحمي القرارات الجوهرية من التفاصيل التقنية**. هذا هو جوهر Clean Architecture بالضبط (سنصل إليه).

### 3. عقلية "كل شيء سيتغيّر" (Design for Change)

السؤال الأهم في الهندسة ليس "كيف أجعله يعمل؟" بل **"ماذا سيحدث عندما يتغيّر هذا الجزء؟"**.

- ماذا لو غيّرنا بوّابة الدفع من Stripe إلى PayPal؟
- ماذا لو أضفنا تطبيق موبايل بجانب الويب؟
- ماذا لو أصبح لدينا مليون منتج بدل ألف؟

لا تبني للحاضر فقط — اعزل الأجزاء المتغيّرة خلف حدود واضحة (Interfaces) حتى يكون التغيير محلياً لا زلزالاً يهز النظام كله.

### الخطوات التي يتبعها المحترف *قبل أول سطر كود* (جواب السؤال 13)

```
1. فهم المشكلة (لماذا نبني هذا أصلاً؟ من المستفيد؟)
2. جمع المتطلبات وتحليلها
3. تحديد الحدود (Scope): ما الذي سنبنيه وما الذي لن نبنيه
4. نمذجة المجال (Domain Model): الكيانات والقواعد
5. تصميم معماري عالي المستوى (Architecture)
6. تصميم قاعدة البيانات و الـ APIs
7. تخطيط الواجهات (Wireframes)
8. إعداد هيكل المشروع والأدوات
9. ← الآن فقط نبدأ الكود
```

لاحظ أن الكود هو الخطوة التاسعة، لا الأولى.

## الجزء الأول: جمع وتحليل المتطلبات (السؤال 1)

### الفرق الجوهري: متطلبات وظيفية vs غير وظيفية

```
المتطلبات الوظيفية (Functional):
   "ماذا يفعل النظام؟"
   - العميل يبحث عن منتجات
   - العميل يضيف منتجاً للسلة
   - المدير يضيف منتجاً جديداً

المتطلبات غير الوظيفية (Non-Functional):
   "كيف يجب أن يكون النظام؟"
   - يتحمّل 10,000 مستخدم متزامن
   - صفحة المنتج تُحمّل في أقل من ثانيتين
   - البيانات الحساسة مشفّرة
```

المبتدئون يركّزون على الوظيفية فقط، ثم يتفاجؤون لاحقاً عندما ينهار النظام تحت الضغط. المحترف يسأل عن الاثنين من اليوم الأول.

### الأداة العملية: قصص المستخدم (User Stories)

حوّل كل متطلب إلى صيغة موحّدة:

```
بصفتي [دور] أريد [هدف] حتى [قيمة/فائدة]
```

أمثلة من متجرنا:

```
- بصفتي زائراً، أريد تصفّح المنتجات حسب الفئة حتى أجد ما أبحث عنه بسرعة.
- بصفتي عميلاً مسجّلاً، أريد إضافة منتجات للسلة حتى أشتريها لاحقاً.
- بصفتي عميلاً، أريد الدفع ببطاقتي حتى أُكمل الطلب دون مغادرة الموقع.
- بصفتي مديراً، أريد رؤية الطلبات الجديدة حتى أجهّزها للشحن.
- بصفتي مديراً، أريد إيقاف منتج نفدت كمّيته حتى لا يطلبه أحد.
```

### تقنية "معايير القبول" (Acceptance Criteria)

كل قصة يجب أن يكون لها معيار يحدّد متى تُعتبر "منجزة". هذه التفاصيل هي التي تكشف القواعد الخفية:

```
القصة: العميل يضيف منتجاً للسلة
معايير القبول:
   ✓ إذا كانت الكمية المطلوبة ≤ المتاح → تُضاف للسلة
   ✗ إذا كانت الكمية > المتاح → تظهر رسالة "الكمية غير متوفرة"
   ✗ إذا كان المنتج موقوفاً → لا يظهر زر الإضافة أصلاً
   ✓ إذا كان المنتج موجوداً في السلة → تُزاد الكمية لا يُكرّر السطر
```

> **نصيحة مهنية:** معايير القبول هي **منجم القواعد التجارية (Business Rules)**. كل "إذا/إلا" هنا سيصبح لاحقاً قاعدة في طبقة الـ Domain. اجمعها بعناية.

### مخرجات هذه المرحلة

1. قائمة قصص المستخدم مع معايير القبول.
2. قائمة المتطلبات غير الوظيفية.
3. تحديد واضح للـ **Scope**: مثلاً "النسخة الأولى لن تدعم: الكوبونات، المرتجعات، نقاط الولاء". تحديد ما **لن** تبنيه لا يقلّ أهمية عمّا ستبنيه.

## الجزء الثاني: من المتطلبات إلى تصميم النظام (السؤال 2)

الآن نحوّل القصص إلى رؤية معمارية. أداتان أساسيتان:

### الأداة 1: تحديد الفاعلين وحالات الاستخدام (Actors & Use Cases)

```
الفاعلون (Actors):
   - زائر (Guest)
   - عميل مسجّل (Customer)
   - مدير (Admin)
   - نظام الدفع الخارجي (Payment Gateway) ← فاعل غير بشري!

حالات الاستخدام لكل فاعل:
   Customer → [تصفّح، بحث، إضافة للسلة، دفع، متابعة طلب]
   Admin    → [إدارة منتجات، إدارة طلبات، تقارير]
```

### الأداة 2: التقسيم إلى مجالات (Bounded Contexts)

هنا يبدأ التفكير المعماري الحقيقي. اجمع القصص المتشابهة في مجموعات منطقية. هذا أهم قرار في المشروع كله:

```
متجرنا الإلكتروني ينقسم إلى:

┌─────────────────────────────────────────────┐
│  Catalog (الكتالوج)                          │
│  المنتجات، الفئات، البحث، التصفية            │
├─────────────────────────────────────────────┤
│  Basket / Cart (السلة)                       │
│  إضافة/إزالة، حساب المجموع المؤقت             │
├─────────────────────────────────────────────┤
│  Ordering (الطلبات)                          │
│  إنشاء طلب، حالات الطلب، تتبّع                │
├─────────────────────────────────────────────┤
│  Payment (الدفع)                             │
│  معالجة الدفع، الفواتير                       │
├─────────────────────────────────────────────┤
│  Identity (الهويّة)                          │
│  تسجيل، دخول، أدوار، صلاحيات                  │
└─────────────────────────────────────────────┘
```

> **لماذا هذا التقسيم بالذات؟** لأن كل مجموعة لها *لغة خاصة وقواعد مستقلة*. "المنتج" في الكتالوج يعني (اسم، سعر، صورة، وصف). نفس "المنتج" في الطلب يعني (اسم وقت الشراء، سعر مجمّد). هذه إشارة على أنهما مجالان مختلفان. عندما تجد أن نفس الكلمة تعني أشياء مختلفة في سياقات مختلفة، فهذه حدود طبيعية بين المجالات.

### مخطّط عالي المستوى للنظام (System Context)

```
[المتصفح/React]  ──HTTP/JSON──►  [ASP.NET Core API]
                                      │
                          ┌───────────┼───────────┐
                          ▼           ▼           ▼
                    [قاعدة البيانات] [بوابة الدفع] [خدمة البريد]
```

هذا الرسم البسيط يجيب عن: ما المكوّنات؟ كيف تتواصل؟ أين الحدود الخارجية؟

## الجزء الثالث: تحديد الكيانات والعلاقات (السؤال 3)

### كيف تكتشف الكيانات؟ تقنية "استخراج الأسماء"

اقرأ قصص المستخدم وضع خطاً تحت كل **اسم (Noun)** مهم. الأسماء المتكرّرة غالباً كيانات:

```
"العميل يضيف منتجاً للسلة ثم يُنشئ طلباً ويدفع..."
   العميل → Customer
   منتج   → Product
   السلة  → Basket
   طلب    → Order
   دفع    → Payment
```

### التمييز بين أنواع الكيانات (مفهوم محترف مهم)

ليست كل الأسماء متساوية. ميّز بينها:

```
Entity (كيان له هويّة مستقلة):
   Product, Order, Customer
   ← له معرّف ID، ويتغيّر عبر الزمن مع بقاء هويّته

Value Object (كائن قيمة، يُعرّف بمحتواه لا بهويّته):
   Money (مبلغ + عملة)، Address (شارع + مدينة + رمز)
   ← لا ID له، عنوانان متطابقان = نفس العنوان

Aggregate (تجمّع، مجموعة كيانات تُعامل كوحدة واحدة):
   Order + OrderItems ← لا تُعدّل OrderItem إلا عبر Order
```

> **لماذا يهم هذا؟** الـ Aggregate هو الذي يحمي تماسك بياناتك. القاعدة "مجموع الطلب = مجموع أسطره" يجب أن تكون مستحيلة الكسر، لذلك نمنع تعديل سطر طلب من خارج الطلب نفسه. الطلب هو "حارس البوّابة" (Aggregate Root).

### تحديد العلاقات

لكل زوج من الكيانات اسأل: ما نوع العلاقة وكم العدد (Cardinality)؟

```
Customer  1 ───── *  Order        (العميل له عدة طلبات)
Order     1 ───── *  OrderItem    (الطلب يحوي عدة أسطر)
OrderItem * ───── 1  Product      (كل سطر يشير لمنتج)
Product   * ───── 1  Category     (كل منتج في فئة)
Order     1 ───── 1  Payment      (لكل طلب دفعة واحدة)
```

ارسمها كمخطّط ERD مبدئي. هذا الرسم سيقودك مباشرة لتصميم قاعدة البيانات.

## الجزء الرابع: تصميم قاعدة البيانات (السؤال 4)

الانتقال من المخطّط المفاهيمي (Entities) إلى المخطّط الفيزيائي (Tables) يتبع قواعد واضحة.

### قاعدة 1: كل Entity → جدول، كل خاصية → عمود

```
Product (الكيان)              Products (الجدول)
   Id                            Id           INT PK
   Name                          Name         NVARCHAR(200)
   Price                         Price        DECIMAL(18,2)
   Description                   Description  NVARCHAR(MAX)
   StockQuantity                 StockQty     INT
   CategoryId                    CategoryId   INT FK
   IsActive                      IsActive     BIT
```

### قاعدة 2: العلاقات تُترجم لمفاتيح أجنبية (Foreign Keys)

```
علاقة 1-إلى-كثير (Customer → Orders):
   ضع FK في الجانب "كثير":
   Orders.CustomerId → Customers.Id

علاقة كثير-إلى-كثير (مثلاً Product ↔ Tag):
   أنشئ جدول وسيط (Join Table):
   ProductTags (ProductId, TagId)
```

### قاعدة 3: التطبيع (Normalization) ثم التحرّر الواعي منه

طبّق قواعد التطبيع لتجنّب تكرار البيانات (كل حقيقة في مكان واحد)، **لكن** اكسرها بوعي حيث يلزم الأداء:

```
مثال على "التحرّر الواعي":
في OrderItem نخزّن ProductName و UnitPrice بشكل مكرّر
رغم وجودهما في Products. لماذا؟
لأن سعر المنتج قد يتغيّر غداً، لكن الفاتورة يجب أن تبقى
كما كانت لحظة الشراء. هذا ليس خطأً — بل قرار تجاري مقصود.
```

### مخطّط قاعدة البيانات لمتجرنا

```
Categories (Id, Name, ParentId?)
    │
    └──< Products (Id, Name, Price, StockQty, CategoryId, IsActive)
              │
              └──< OrderItems (Id, OrderId, ProductId, ProductName, UnitPrice, Quantity)
                        │
                        └──> Orders (Id, CustomerId, Status, TotalAmount, CreatedAt)
                                  │
                                  ├──> Customers (Id, Name, Email, PasswordHash)
                                  └──< Payments (Id, OrderId, Amount, Method, Status)
```

### قرارات تقنية يجب اتخاذها هنا

- **نوع المفتاح:** عدد متسلسل (Identity) أم GUID؟ (Identity أبسط وأسرع، GUID أفضل للتوزيع).
- **الفهارس (Indexes):** أي أعمدة سنبحث بها كثيراً؟ (مثلاً `Products.CategoryId`, `Orders.CustomerId`) — فهرسها.
- **الحذف:** حذف فعلي أم منطقي (Soft Delete عبر عمود `IsDeleted`)؟ في التجارة عادةً منطقي للحفاظ على السجلات.

## الجزء الخامس: تصميم الـ APIs (السؤال 5)

### المبدأ: الـ API يعكس "الموارد" و"الأفعال" عليها

في REST، فكّر بالأسماء (موارد) لا الأفعال. الفعل يأتي من نوع طلب HTTP:

```
المورد: المنتجات (Products)

GET    /api/products              ← اجلب كل المنتجات (مع ترقيم وتصفية)
GET    /api/products/{id}         ← اجلب منتجاً واحداً
POST   /api/products              ← أنشئ منتجاً (Admin)
PUT    /api/products/{id}         ← عدّل منتجاً كاملاً
PATCH  /api/products/{id}         ← عدّل جزئياً (مثلاً السعر فقط)
DELETE /api/products/{id}         ← احذف منتجاً
```

### اشتقاق الـ APIs من قصص المستخدم

كل قصة مستخدم → عملية API واحدة أو أكثر:

```
القصة: "العميل يضيف منتجاً للسلة"
   POST /api/basket/items
   Body: { productId: 5, quantity: 2 }

القصة: "العميل يُتمّ الطلب"
   POST /api/orders
   Body: { basketId: "...", shippingAddress: {...} }

القصة: "العميل يتابع طلبه"
   GET /api/orders/{id}
```

### تصميم العقد (Contract): الطلب والاستجابة

حدّد شكل البيانات بدقّة *قبل* البرمجة. هذا "عقد" بين الـ Frontend والـ Backend:

```
POST /api/orders
Request:
{
  "items": [{ "productId": 5, "quantity": 2 }],
  "shippingAddress": { "street": "...", "city": "..." }
}

Response 201 Created:
{
  "orderId": 1023,
  "status": "Pending",
  "totalAmount": 49.98,
  "createdAt": "2026-06-13T10:00:00Z"
}

Response 400 Bad Request:
{
  "error": "InsufficientStock",
  "message": "الكمية المطلوبة غير متوفرة للمنتج رقم 5"
}
```

### مبادئ احترافية في تصميم الـ API

```
✓ استخدم رموز حالة HTTP الصحيحة:
   200 OK، 201 Created، 400 خطأ في الطلب،
   401 غير مُصرّح، 403 ممنوع، 404 غير موجود، 500 خطأ خادم

✓ النُسخ (Versioning): /api/v1/products ← حتى لا تكسر العملاء القدامى عند التطوير

✓ الترقيم (Pagination): /api/products?page=2&pageSize=20
   لا تُرجع 10,000 منتج دفعة واحدة أبداً

✓ التصفية والفرز: /api/products?category=5&sort=price_asc

✓ لا تُسرّب كيانات قاعدة البيانات مباشرة — استخدم DTOs
   (نماذج نقل بيانات مخصّصة للـ API)
```

> **مفهوم محترف: DTO.** لا تُرجع كيان `Product` الداخلي للـ API مباشرة. أنشئ `ProductDto` يحوي فقط ما يحتاجه العميل. لماذا؟ لئلا يرى العميل حقولاً داخلية (مثل تكلفة الشراء)، ولئلا يتعطّل الـ Frontend عندما تُعدّل بنية الكيان الداخلي.

## الجزء السادس: تخطيط الشاشات قبل البرمجة (السؤال 6)

### لا ترسم بكسلات — ارسم هياكل (Wireframes)

قبل أي CSS، ارسم مخطّطات منخفضة الدقّة (حتى على ورق). الهدف: ترتيب المحتوى والتدفّق، لا الجمال.

```
شاشة قائمة المنتجات:
┌────────────────────────────────────┐
│  [Logo]   [بحث.........]  [🛒 السلة] │
├────────────────────────────────────┤
│ الفئات │   [صورة] [صورة] [صورة]      │
│ • ملابس│   اسم     اسم     اسم        │
│ • أحذية│   سعر     سعر     سعر        │
│ • حقائب│   [أضف]   [أضف]   [أضف]      │
│        │   [صورة] [صورة] [صورة]      │
│        │   ◄ 1 2 3 4 ►   (ترقيم)     │
└────────────────────────────────────┘
```

### اشتق الشاشات من رحلة المستخدم (User Journey)

تتبّع رحلة العميل من البداية للنهاية، وستظهر لك الشاشات تلقائياً:

```
الصفحة الرئيسية → قائمة المنتجات → صفحة منتج →
السلة → تسجيل الدخول → عنوان الشحن →
الدفع → تأكيد الطلب → متابعة الطلب
```

كل سهم هنا = انتقال (Navigation)، وكل صندوق = شاشة (Component/Page في React).

### اربط كل شاشة بالـ API الذي تحتاجه

هذه الخطوة تكشف الثغرات مبكراً:

```
شاشة قائمة المنتجات → GET /api/products
شاشة المنتج         → GET /api/products/{id}
السلة               → GET/POST /api/basket
تأكيد الطلب         → POST /api/orders
متابعة الطلب        → GET /api/orders/{id}
```

إذا وجدت شاشة بلا API، أو API بلا شاشة → لديك خلل في التخطيط اكتشفته قبل أن يكلّفك أسابيع.

## الجزء السابع والثامن: هيكل المشروع و Clean Architecture (السؤالان 7 و8)

هذا قلب سؤالك. دعنا نفهم Clean Architecture **بالحدس أولاً** ثم بالتطبيق.

### الفكرة الأساسية: دوائر متحدة المركز

تخيّل النظام كدوائر. القاعدة الوحيدة: **التبعيات تشير للداخل فقط**. الداخل لا يعرف شيئاً عن الخارج.

```
        ┌─────────────────────────────────────┐
        │         Presentation / API          │  ← الأبعد عن المركز
        │   ┌─────────────────────────────┐   │
        │   │      Infrastructure         │   │
        │   │   ┌─────────────────────┐   │   │
        │   │   │    Application      │   │   │
        │   │   │  ┌───────────────┐  │   │   │
        │   │   │  │    Domain     │  │   │   │  ← القلب
        │   │   │  │ (القواعد)     │  │   │   │
        │   │   │  └───────────────┘  │   │   │
        │   │   └─────────────────────┘   │   │
        │   └─────────────────────────────┘   │
        └─────────────────────────────────────┘

السهم دائماً للداخل:  API → Infrastructure → Application → Domain
Domain لا يعتمد على أحد.  ✓ هذا يحمي قواعدك من تقلّبات التقنية.
```

### ماذا في كل طبقة؟

```
┌─ Domain (القلب) ───────────────────────────────────┐
│ • الكيانات: Product, Order, OrderItem               │
│ • كائنات القيمة: Money, Address                      │
│ • القواعد التجارية: "لا يمكن طلب كمية > المتاح"      │
│ • واجهات المستودعات: IProductRepository (تعريف فقط)  │
│ ✗ لا يعرف شيئاً عن SQL أو ASP.NET أو JSON            │
└─────────────────────────────────────────────────────┘

┌─ Application (حالات الاستخدام) ────────────────────┐
│ • الأوامر والاستعلامات: CreateOrderCommand          │
│ • معالجاتها (Handlers): منطق تنسيق العملية           │
│ • DTOs و واجهات الخدمات: IPaymentService             │
│ • التحقق (Validation)                                │
│ ✗ لا يعرف كيف تُنفّذ التفاصيل، فقط ماذا يُفعل         │
└─────────────────────────────────────────────────────┘

┌─ Infrastructure (التفاصيل التقنية) ────────────────┐
│ • تنفيذ المستودعات: ProductRepository (بـ EF Core)   │
│ • قاعدة البيانات: DbContext                          │
│ • تنفيذ الخدمات الخارجية: StripePaymentService       │
│ • إرسال البريد، رفع الملفات                          │
│ ✓ هنا تعيش كل التقنيات القابلة للاستبدال             │
└─────────────────────────────────────────────────────┘

┌─ Presentation / API (الواجهة) ─────────────────────┐
│ • Controllers (نقاط النهاية)                         │
│ • Middleware (المصادقة، معالجة الأخطاء)              │
│ • إعداد الحقن (Dependency Injection)                 │
│ ✓ يستقبل HTTP ويُحوّله لأوامر Application             │
└─────────────────────────────────────────────────────┘
```

## الجزء التاسع: المكوّنات والأنماط القابلة لإعادة الاستخدام (السؤال 9)

لا تُعد اختراع العجلة. هذه الأنماط جاهزة ومجرّبة:

### في الـ Backend

```
1. Repository Pattern
   واجهة موحّدة للوصول للبيانات. اكتب IGenericRepository<T>
   مرة، واستخدمه لكل الكيانات.

2. Unit of Work
   يضمن أن عدة تغييرات تُحفظ معاً أو تُلغى معاً (Transaction).

3. CQRS + Mediator (مكتبة MediatR)
   فصل الأوامر (تُعدّل) عن الاستعلامات (تقرأ).
   كل Handler منعزل وقابل للاختبار.

4. Result Pattern
   بدل رمي الاستثناءات للأخطاء المتوقّعة، أرجِع
   Result<T> يحوي إما النجاح أو الخطأ بشكل صريح.

5. Specification Pattern
   لتغليف شروط الاستعلام المعقّدة وإعادة استخدامها.

6. Middleware للأمور المتقاطعة (Cross-Cutting):
   معالجة الأخطاء، التسجيل (Logging)، المصادقة
   — تُكتب مرة وتُطبّق على كل الطلبات.
```

مثال على القاعدة المعمّمة (Base Entity):

```csharp
// يرثها كل كيان — لا تكرّر Id و التواريخ في كل مرة
public abstract class BaseEntity
{
    public int Id { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime? UpdatedAt { get; set; }
}
```

### في الـ Frontend (React)

```
1. مكوّنات واجهة معمّمة (UI Components):
   <Button>, <Modal>, <Input>, <Card>, <Spinner>
   اكتبها مرة، استخدمها في كل مكان.

2. Custom Hooks لإعادة استخدام المنطق:
   useFetch(url)        ← جلب بيانات + حالات التحميل/الخطأ
   useDebounce(value)   ← لتأخير البحث
   useCart()            ← منطق السلة

3. طبقة API موحّدة:
   ملف apiClient.js واحد يعالج الـ baseURL والـ headers
   والـ tokens — لا تكرّر إعدادات fetch في كل مكوّن.

4. Layout Components:
   <MainLayout>, <AdminLayout> ← الهيكل المشترك للصفحات.

5. إدارة الحالة (State Management):
   Context API أو Redux/Zustand للحالة المشتركة
   (المستخدم الحالي، محتوى السلة).
```

> **القاعدة:** إذا كتبت نفس الشيء مرتين، فكّر. إذا كتبته ثلاث مرات، جرّده في مكوّن/دالة قابلة لإعادة الاستخدام (مبدأ DRY — لا تكرّر نفسك).

## الجزء العاشر: تقسيم النظام إلى وحدات/ميزات (السؤال 10)

### استراتيجيتان للتنظيم — اختر "حسب الميزة"

```
✗ التنظيم حسب النوع التقني (Layer-by-Type):
   /Controllers  → كل الـ controllers معاً
   /Services     → كل الخدمات معاً
   /Models       → كل النماذج معاً

   المشكلة: لإضافة ميزة "الكوبونات" تقفز بين 5 مجلدات.

✓ التنظيم حسب الميزة (Feature-by-Folder):
   /Features/Products/   → كل ما يخص المنتجات هنا
   /Features/Orders/     → كل ما يخص الطلبات هنا
   /Features/Coupons/    → ميزة جديدة؟ مجلد واحد جديد

   الفائدة: الميزة كاملة في مكان واحد، سهلة الإضافة والحذف.
```

### مبدأ "الحدّ من الترابط، وزيادة التماسك"

```
التماسك العالي (High Cohesion):
   كل ما يخص الطلبات في وحدة Orders. الأشياء المترابطة معاً.

الترابط المنخفض (Low Coupling):
   وحدة Orders لا تعرف التفاصيل الداخلية لوحدة Payment.
   تتواصلان عبر واجهة واضحة (Interface) فقط.

النتيجة: تستطيع تعديل وحدة دون كسر الأخرى.
```

### كيف تقرّر حدود الوحدة؟ اختبار بسيط

اسأل: *"لو حذفت هذه الميزة بالكامل، كم ملفاً سأمسّ؟"*
- إذا كانت كل ملفاتها في مجلد واحد → تنظيم ممتاز.
- إذا كانت متناثرة في كل مكان → ترابط سيّئ، أعد التفكير.

```
وحدات متجرنا، كل واحدة شبه مستقلّة:
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Catalog  │  │  Basket  │  │ Ordering │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     └─── واجهات واضحة بينها ─────┘
         (لا اعتماد على التفاصيل الداخلية)
```

## الجزء الحادي عشر: إدارة الفوضى وكثرة الملفات (السؤال 11)

شعور التشتّت حقيقي، وله حلول هندسية:

### 1. التسمية المتّسقة (Naming Conventions)

عندما تتّبع نمطاً ثابتاً، يصبح اسم الملف عنواناً يقودك:

```
CreateProductCommand.cs        ← أمر
CreateProductHandler.cs        ← معالجه
CreateProductValidator.cs      ← مدقّقه
GetProductsQuery.cs            ← استعلام
ProductDto.cs                  ← نموذج نقل
ProductsController.cs          ← نقطة النهاية
IProductRepository.cs          ← واجهة (تبدأ بـ I)
ProductRepository.cs           ← تنفيذها
```

بمجرد رؤية الاسم تعرف نوع الملف ودوره وأين يقع — دون فتحه.

### 2. مبدأ "القرب" (Proximity / Screaming Architecture)

الملفات المتغيّرة معاً تعيش معاً. عندما تفتح مجلد المشروع يجب أن "يصرخ" بما يفعله النظام:

```
عند فتح /Features ترى فوراً:
   Products/  Orders/  Basket/  Payments/
   
هذا يخبرك أن النظام "متجر"، لا أنه "ASP.NET app"
المعمارية تعكس المجال، لا التقنية.
```

### 3. خريطة ذهنية واحدة للمشروع (Architecture Map)

احتفظ بملف `ARCHITECTURE.md` يحوي:
- مخطّط الطبقات.
- قائمة الوحدات ومسؤولية كل منها.
- قواعد "أين يذهب كل نوع كود".

عندما تتشتّت، ارجع لهذه الخريطة بدل التيه في الملفات.

### 4. قاعدة "افتح ما تحتاجه فقط"

لا تحاول حمل المشروع كله في رأسك. اعمل على ميزة واحدة في وقت واحد. الـ Clean Architecture مصمّمة تحديداً ليتيح لك العمل على Orders دون فتح أي ملف من Catalog.

### 5. أدوات المحرّر

استخدم:
- البحث بالرمز (Go to Symbol) بدل التصفّح اليدوي.
- إشارات مرجعية (Bookmarks) للملفات النشطة.
- مجموعات علامات تبويب (Tab Groups) لكل ميزة.

## الجزء الثاني عشر: التوثيق والحفاظ على الرؤية (السؤال 12)

### وثّق القرارات، لا الكود

الكود الجيّد يشرح *كيف*. التوثيق يشرح *لماذا*. ركّز على الثاني:

```
ملفات التوثيق الأساسية للمشروع:

README.md          ← ما هو المشروع، كيف تشغّله، التقنيات
ARCHITECTURE.md    ← الطبقات، الوحدات، القواعد المعمارية
DOMAIN.md          ← الكيانات، القواعد التجارية، المصطلحات
API.md / Swagger   ← توثيق نقاط النهاية (يُولّد آلياً)
CONTRIBUTING.md    ← معايير الكود والتسمية للفريق
```

### سجلّ قرارات المعمارية (ADR)

أقوى أداة لمنع نسيان "لماذا فعلنا هذا؟". لكل قرار مهم اكتب ملفاً قصيراً:

```
ADR-003: استخدام Soft Delete للطلبات

السياق: نحتاج حذف طلبات، لكن المحاسبة تتطلب سجلات دائمة.
القرار: لن نحذف الطلبات فعلياً، بل نعلّمها IsDeleted=true.
البدائل المرفوضة: الحذف الفعلي (يفقد السجل المحاسبي).
النتائج: كل الاستعلامات يجب أن تُصفّي المحذوفات.
التاريخ: 2026-06-13
```

بعد ستة أشهر، عندما تسأل "لماذا لا نحذف الطلبات فعلياً؟"، الجواب موثّق.

### وثّق آلياً حيثما أمكن

```
✓ Swagger/OpenAPI: يولّد توثيق الـ API من الكود تلقائياً.
✓ تعليقات XML على نقاط النهاية → تظهر في Swagger.
✓ مخطّط قاعدة البيانات: يُولّد من EF Core Migrations.
```

التوثيق اليدوي يتعفّن (يصبح قديماً). الآلي يبقى محدّثاً.

### الحفاظ على الرؤية أثناء التطوير

```
1. ابدأ كل يوم بنظرة على لوحة المهام (Backlog/Board).
2. اعمل على ميزة كاملة (عمودياً عبر كل الطبقات) لا طبقة كاملة.
3. أغلق كل ميزة باختبار وتوثيق قبل الانتقال للتالية.
4. راجع ARCHITECTURE.md دورياً — هل ما زال يصف الواقع؟
```

## الجزء الثالث عشر والرابع عشر: العقلية التحليلية ورؤية الصورة الكاملة (السؤالان 13 و14)

### تمرين عملي لبناء العقلية التحليلية

كلما واجهت مشروعاً، طبّق هذه الأسئلة الخمسة بالترتيب:

```
1. لماذا؟   (الهدف التجاري — ما المشكلة الحقيقية؟)
2. من؟      (الفاعلون — من يستخدم النظام؟)
3. ماذا؟    (الميزات — ما الذي يجب أن يفعله؟)
4. كيف؟     (المعمارية — كيف ننظّمه؟)
5. ماذا لو؟ (التغيير — كيف سيتطوّر؟)
```

المبتدئ يقفز مباشرة إلى سؤال "كيف أكتب الكود؟". المحترف يقضي 70% من وقته في الأسئلة 1–3 قبل لمس لوحة المفاتيح.

### من "الملفات الفردية" إلى "الصورة الكاملة"

```
انتقل في تفكيرك عبر مستويات التجريد:

السطر  → الدالة → الصنف → الوحدة → النظام → المنظومة
(كود)                              (معمارية)      (سياق)

المهندس يتنقّل بين هذه المستويات بمرونة:
- يكبّر (Zoom in) لحل مشكلة في دالة.
- يصغّر (Zoom out) ليرى كيف تؤثّر على النظام كله.

المبتدئ عالق في مستوى "السطر والدالة" فقط.
```

### عادات تبني عقلية المهندس

```
✓ ارسم قبل أن تكتب: كل ميزة ابدأها بمخطّط على ورق.
✓ فكّر بالحالات الحدّية: ماذا لو فشل الدفع منتصف العملية؟
✓ اسأل "ماذا يتغيّر؟" قبل "كيف أبني؟".
✓ اقرأ كوداً جيّداً لمشاريع مفتوحة المصدر بنفس المعمارية.
✓ اشرح تصميمك بصوت عالٍ — إن لم تستطع شرحه ببساطة فلم تفهمه.
✓ راجع قراراتك بأثر رجعي: ما الذي كنت سأفعله مختلفاً؟
```

## الخلاصة: نموذج العمل القابل للتطبيق على أي مشروع (Roadmap)

هذا هو الإطار الكامل الذي تطبّقه على *أي* مشروع متوسط أو كبير:

```
المرحلة 1 — الفهم (Discovery)
   □ افهم المشكلة والهدف التجاري
   □ حدّد الفاعلين
   □ اكتب قصص المستخدم + معايير القبول
   □ اجمع المتطلبات غير الوظيفية
   □ حدّد الـ Scope (ما ستبنيه وما لن تبنيه)

المرحلة 2 — التحليل (Analysis)
   □ قسّم النظام لمجالات (Bounded Contexts)
   □ استخرج الكيانات والعلاقات
   □ ميّز Entities / Value Objects / Aggregates
   □ ارسم ERD مبدئي

المرحلة 3 — التصميم (Design)
   □ صمّم قاعدة البيانات (جداول، مفاتيح، فهارس)
   □ صمّم عقود الـ API (موارد، أفعال، DTOs)
   □ ارسم Wireframes للشاشات
   □ اربط كل شاشة بالـ API الخاص بها
   □ اختر المعمارية (Clean Architecture)

المرحلة 4 — الإعداد (Setup)
   □ أنشئ هيكل المشروع (الطبقات والمجلدات)
   □ اضبط أدوات البناء، Git، CI
   □ أنشئ README و ARCHITECTURE.md
   □ جهّز المكوّنات المعمّمة (Base classes, UI components)

المرحلة 5 — البناء (Build) — ميزة ميزة، عمودياً
   □ لكل ميزة: Domain → Application → Infrastructure → API → UI
   □ اكتب الاختبارات مع الكود
   □ وثّق القرارات المهمة (ADR)

المرحلة 6 — المراجعة المستمرة (Iterate)
   □ راجع: هل المعمارية ما زالت تخدم الأهداف؟
   □ أعد الهيكلة (Refactor) عند تراكم الديون التقنية
   □ حدّث التوثيق ليطابق الواقع
```

### المبدأ الواحد الذي يجمع كل ما سبق

> **افصل ما يتغيّر بسرعة عمّا يتغيّر ببطء، واجعل الأشياء بطيئة التغيّر (القواعد التجارية) لا تعتمد أبداً على الأشياء سريعة التغيّر (التقنيات والواجهات).**

هذا هو جوهر الهندسة. كل نمط وكل طبقة وكل قرار في هذا المستند ليس إلا تطبيقاً لهذا المبدأ الواحد.
