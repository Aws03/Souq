# Release readiness

> **What this page is:** every known blocker between Souq today and a first paying customer, triaged by severity, with the evidence that it is real, what closing it takes, and what proves it closed. It is the page to read before saying "we can go live".
> **How it differs from its neighbours:** [RiskRegister.md](../02-ARCHITECTURE/RiskRegister.md) says *how this system can hurt someone*; [TechnicalDebt.md](../12-ROADMAP/TechnicalDebt.md) says *what we chose to postpone*; this page says **what stops a release**, and tracks each item to closed.
> **Checklist for the release itself:** [ProductionReleaseChecklist.md](ProductionReleaseChecklist.md).

## How this page is built

Every item below was **re-verified against the code during Phase 17**, not copied forward. Where the earlier register's description turned out to be incomplete or wrong, this page says so. Items numbered `F-*` were **found in Phase 17** and have no entry in the older registers; `F-7` onward came out of the transaction, concurrency, idempotency and tenant-isolation audits, and each was confirmed by reading the code rather than taken from the audit report.

Numbers are never reused. `F-5` is absent because it was closed, not forgotten.

**Severity**

| | Meaning |
|---|---|
| **P0** | Must be closed before any real customer or real money. Money loss, data loss, a broken deployment, or a legal bar |
| **P1** | Should be closed before the first commercial customer. Correctness or security weakness with a workaround, or an operational gap |
| **P2** | Acceptable to ship with a written limitation |
| **P3** | Future improvement; no release depends on it |

**Status**

`FIXED (Phase 17)` · `OPEN` · `BLOCKED — owner decision` · `BLOCKED — external verification` · `ACCEPTED — documented limitation`

**Evidence** is either *verified in code* (someone read the path and can name it), *reproduced* (a test or a run demonstrates it), or *inherited* (carried from an earlier pass and re-read, but the failure has not been reproduced).

| R-02 | **A declined card could capture money against a cancelled order.** A `payment_intent.payment_failed` webhook cancelled the order while the intent stayed alive at `requires_payment_method`; the shopper retried on the same client secret, the money was captured, and the later success found a non-`Pending` order and returned an idempotent success. | R-13 | **Every uploaded image and store logo 404s through the shipped stack.** `/uploads/` was proxied with no `Host` override, so nginx sent `Host: api:8080`; `TenantResolutionMiddleware` runs on `/uploads`, resolves the store from the host, finds none, and answers `404 StoreNotFound` | Verified in code: the `/api/` location sets `proxy_set_header Host $http_host`, the `/uploads/` location set nothing | `frontend/nginx.conf` now forwards `Host`, `X-Forwarded-For` and `X-Forwarded-Proto` on `/uploads/` exactly as on `/api/` | *Needs a running stack to prove; no automated test covers the proxy* | **FIXED (Phase 17)** |
| R-17 | **A fresh production database is seeded with demo data.** `DbSeeder` applied the demo store's branding, three categories, eight products and their stock unconditionally — the environment was never consulted | Verified in code: `SeedCatalogAsync` and `ApplyDefaultStoreLookAsync` were gated only on "has no categories yet" and "settings never customised" | `DbSeeder.ShouldSeedDemoData` gates both on the environment, overridable in either direction by `Seed:DemoData`. Production initialization now keeps only what is configured deliberately (platform owner, first admin, host binding), and the seeder logs that demo data was skipped | `ConfigurationTests` (the decision table, including the explicit override in both directions) | **FIXED (Phase 17)** |
| R-06 | **The order confirmation email prints the wrong total, or never arrives.** `OrderEmailHandler` loaded the order through `GetByIdAsync`, which is `FindAsync` — the root alone, no lines. `Order.TotalAmount` then summed an empty collection, so the email showed shipping only; with a coupon, `Subtotal.Subtract(DiscountAmount)` went negative and `Money` threw, so the message retried until the outbox marked it dead | Verified in code: `OrderRepository` overrides only `GetWithItemsAsync`; nothing configures an auto-include | The handler loads the whole aggregate and reports the **frozen** figures (`PlacedSubtotal`, `PlacedTotal`) rather than recomputing at send time; the email is itemised, and the discount and shipping rows appear only when they exist | `OrderNotificationHandlersTests` (lines, a discount and shipping from the frozen columns; no discount or shipping row when there is none), `NotificationTests` (the delivered email carries the purchased line and the right total) | **FIXED (Phase 17)** |

This is a deployment action, not a code change | *None — no test can assert the deployment's credentials* | **OPEN — deployment action** |
| R-16 | **No TLS, HSTS or security headers in the repository's own deployment**, and nginx overwrites `X-Forwarded-Proto` with its own (plain http) scheme, so links generated for emails can come out `http://` | Verified in code: nginx listens on port 80 only; the API calls neither HTTPS redirection nor HSTS | Terminate TLS in front, pass the outer scheme through instead of overwriting it, and add the header set before any public launch | `StartupAndSecurityTests` covers the API's own headers only | **OPEN — deployment action** |
| R-19 | **No automated backups and no rehearsed restore.** Data loss is unbounded, and `SECRETS_KEY` is unrecoverable — without it every stored store payment key is permanently unreadable | Verified: no backup job, schedule or script exists in the repository | Define and **rehearse** backup and restore of the database, the uploads volume and the secrets together, before the first paying store | *None* | **OPEN — operational** |

## P1 — should be closed before the first commercial customer

| # | Blocker | Evidence | Remediation | Tests | Status |
|---|---|---|---|---|---|
| R-08 | **A suspended store answers 503 to everything**, including its own storefront configuration and sign-in, so it cannot show a branded "closed" page and its administrators cannot sign in to fix anything. `AvailableWhenStoreClosedAttribute` exists and is honoured — and was applied to **no endpoint** | Verified in code: a repository-wide search found the attribute only in its own definition, in `TenantAvailabilityMiddleware.IsOpen`, and in the documentation generator | The attribute is applied to exactly five endpoints — the storefront configuration, sign-in, refresh, sign-out and "who am I" — endpoint by endpoint rather than to a whole controller, so registration, password reset and every permission-protected endpoint stay closed. **Still open as a product decision:** how much administration a suspended store should retain beyond signing in (see P1 below) | `TenantResolutionTests` (catalog 503, config 200, admin signs in, admin endpoints still 503, registration 503) | **FIXED (Phase 17)** |
| R-07 | **A product in a disabled category is hidden but still purchasable.** `CatalogQueries.VisibleProducts` filtered on the category, but `PricingService` marked a line sellable from `Product.IsActive` alone, and checkout trusted that flag | Verified in code across the storefront, basket and checkout paths | Sellability is now one rule in the Domain — `Product.IsSellable` requires an active product **and** an active category — enforced by the pricing pipeline (so the basket and checkout share it), the basket add and the wishlist. `ProductRepository` loads the category with the aggregate | `ProductTests`, `PricingServiceTests`, `BasketHandlersTests`, `WishlistHandlersTests`, `CatalogTests` (a basket filled before the category is disabled, a fresh add, a direct checkout, and re-activation) | **FIXED (Phase 17)** |
| R-10 | **The public order tracking token is written to the request log.** `RequestLoggingMiddleware` logs `Request.Path`, and the token is a path segment of `/api/orders/track/{token}`; nginx's default access log records it too | Verified in code | Sensitive route parameters are redacted by **value** from the logged path, keeping the route template for aggregation. **Remaining gap (G-03):** the proxy's access log still records the SPA's token-bearing query strings for reset, verification and invitation links — a log-policy decision at the proxy | `ObservabilityTests` (the path is `/api/orders/track/***`, the template survives, the token is in no log entry) | **FIXED (Phase 17) — API side; proxy log policy still open** |
| R-22 | **`.env.example` shipped a non-empty Gmail placeholder**, which defeats the "no email provider" fail-fast: the API starts, selects Gmail, and every message dies after eight attempts | Verified in code: `AddEmail` selects Gmail on any non-empty `Gmail:AppPassword` | The placeholder is now empty, with the consequence written next to it | `NotificationTests` proves the fail-fast itself | **FIXED (Phase 17)** |
| TD-26 | **One transient failure of the payment-config request disabled card payment for the whole session.** `getStripePromise` cached `.catch(() => null)`, and `CardPaymentForm` reads `null` as "this store has no gateway" — so a momentary network error showed the shopper a "pay now" button with no card field. Pressing it confirms an order against an intent that never received a payment method, which since [ADR-0036](../11-ADR/0036-payment-intent-state-machine.md) answers a retryable `PaymentFailed` | Verified in code: one `catch` mapped every failure, transient or not, to "not configured", and the result was memoised for the lifetime of the page | The two answers are now distinguished: an empty key is a real, cacheable answer (no gateway — the direct-pay fallback is correct); a failed request is not cached and is re-asked, and the screen shows an error with a retry instead of silently degrading | `stripeClient.test.js` (a failure is re-asked, a real key loads Stripe once, an empty key is cached as "no gateway") | **FIXED (Phase 17)** |
| F-7 | **Disabling two administrators at once can leave a store — or the platform — with none.** `AccountStatusChanger.SetActiveAsync` counts active holders of the last-standing role, then disables *this* user and saves | **Found in Phase 17.** Verified in code: the count at `CountActiveByRoleAsync` and the write are separated, and the two requests write **different `User` rows**, so the rowversion on `User` never fires. A post-write re-count does not help either: under READ COMMITTED each transaction still sees the other's administrator as active | Needs real serialization — a stricter isolation level for this one operation, or a shared row both requests contend on. `IUnitOfWork` (a **Domain** interface) exposes no isolation level, and locking hints are raw SQL, which `TenancyRuleTests` forbids. So the fix is an architectural change, not a patch: **an owner/architecture decision**. Recovery today: a platform owner re-enables a store's administrator — but a locked-out **platform owner** has no in-product recovery at all | `AccountsTests` covers the sequential guard (`لا_يُوقف_آخر_مدير_فعّال`) with a stubbed count; the race is **NONE** | **OPEN — architecture decision** |
| F-8 | **A double-submitted checkout creates two orders**, double-reserving stock and spending two coupon uses from one basket | **Found in Phase 17.** Verified in code: `CreateOrderCommand` carries no idempotency key or client request id, `OrdersController.Create` carries no rate-limit policy (only Auth, Refresh, CouponPreview and Basket exist), and `CreateOrderHandler` has no precondition on an existing `Pending` order. The `BasketEmpty` guard does **not** cover this — the basket is emptied at payment, not at order creation, so a second checkout re-reads the same lines | No double charge (one client secret is rendered), and `ExpireStaleCheckoutsHandler` reclaims the stock and the coupon after `Inventory:ReservationMinutes`. Until then the shopper's *own* second click can fail with `InsufficientStock` on a low-stock item. **What a duplicate checkout should do — reject it, or return the order already created — is a commercial choice, so it is the owner's**: the engineering options are an idempotency key on the command, a pending-order precondition, or a rate-limit policy on the endpoint | **NONE** | **OPEN — owner decision** |
| F-9 | **The first two simultaneous orders in a new store could fail one of them with `409 DuplicateValue`.** `OrderNumbers` creates the store's counter row on first use and retried on a unique-index race — except the retry could never run | **Found in Phase 17.** Verified by type analysis: `AppDbContext.SaveChangesAsync` translates SQL 2601/2627 into `UniqueConstraintViolationException`, which derives from `Exception`, **not** `DbUpdateException` — so `catch (DbUpdateException)` was unreachable and the file's own comment described behaviour that never happened | The catch now names `UniqueConstraintViolationException`, with the reason recorded next to it so it is not "simplified" back | Covered indirectly by `OrderLifecycleTests` (`أرقام_الطلبات_متسلسلة_لكل_متجر_من_1001`, sequential); the concurrent first-order race itself is **NONE** — it is not deterministically reproducible without controlling transaction timing | **FIXED (Phase 17)** |
| F-10 | **Every deployment could duplicate an in-flight notification email.** `OutboxProcessor` sent the message, then recorded `ProcessedAt` with the dispatch token | **Found in Phase 17.** Verified in code: the success write passed `ct` while `RecordFailureAsync` deliberately passed `CancellationToken.None`. On shutdown between "email sent" and "row marked processed", the write was cancelled, the catch filter declined the `OperationCanceledException`, and the row stayed unprocessed and leased — re-sent once the lease expired | The success write is now uncancellable too, matching the failure path: the message has already left the system, so recording that is bookkeeping, not work to abandon | **NONE.** Not deterministically testable with the current harness: `CapturingEmailSender.Block()` gates on the dispatch token, so cancelling before release cancels the send itself and never reaches the write being fixed | **FIXED (Phase 17)** |

Both change staff workflow, so the choice is the owner's | `UpdateOrderStatusHandlerTests`, `AuthorizationMatrixTests` | **OPEN — owner decision** |
| R-11 | **Rate limits are per process and partition on a forwarded client address.** With the API port published and the Docker bridge inside `TRUSTED_PROXY_NETWORKS`, a direct client may forge `X-Forwarded-For` | Inherited; depends on the deployment's networking and was not reproduced | Do not publish the API port when a proxy fronts the stack; trust only the proxy's own address; move limits to the edge when scaling out | `AuthSessionTests` covers the limiter, not the spoofing path | **OPEN — deployment action** |
| R-20 | **No health checks and no CI pipeline.** A broken deploy is found by a customer; a red suite can be committed | Verified: no health endpoint is mapped and no CI configuration exists | Add a health endpoint and a pipeline running the five suites. ## Not yet assessed

These are named in the mission and not yet re-verified in code; they carry no severity until they are.

- Performance: N+1 queries and unbounded reads on the admin and reporting paths.

**Assessed during Phase 17 and no longer on this list:**

- **Transaction boundaries and concurrency.** No use case splits a logical write across transactions that should be one, and **no transaction spans a network call** — the rule ADR-0021 states is genuinely kept: `CreateOrderHandler` creates the payment intent after its commit, `UpdateOrderStatusCommand` refunds after its commit, and `OrderPaymentConfirmation` confirms before opening one. Every contended aggregate carries a rowversion (Product, Coupon, Order, Payment, InventoryItem, Tenant, User); the four that do not — `CouponRedemption`, `Refund`, `StockReservation`, `Basket` — are covered by their aggregate root's token or, for the basket, deliberately last-writer-wins with checkout re-validating. The open items are F-7 and F-8.
- **Idempotency.** Duplicate Stripe webhooks, duplicate `confirm-payment`, refund retries and coupon reserve/confirm/release are all protected, and the mechanism is worth knowing: the webhook handler **discards the event's payload and type** and re-asks the gateway for the intent's live state, which is what makes both redelivery and out-of-order delivery safe without a processed-events table. Order creation (F-8) is the one unprotected entry point.
- **Tenant isolation.** Audited across all 13 modules against the controllers rather than the generated inventory: no cross-tenant or cross-customer path was found. Every mechanism ADR-0022 claims was confirmed present and applied by reflection across the model, and `TenantIsolationTests` enumerates the live endpoint list so the matrix cannot silently drift. The residual items are F-1 and F-2, both already recorded.

## How to use this page

1. **Before a release:** everything in P0 is either `FIXED` or has a deliberate, written acceptance from the owner. No exceptions — P0 is defined as "money, data, deployment or law".
2. **Before the first commercial customer:** work down P1. Items marked *owner decision* cannot be closed by engineering alone; take them to the owner as a batch.
3. **When an item closes:** move it to `FIXED` with the commit, and delete its row from [RiskRegister.md](../02-ARCHITECTURE/RiskRegister.md) and its entry in [TechnicalDebt.md](../12-ROADMAP/TechnicalDebt.md) in the same change. This page keeps the history; those two keep only what is still true.
