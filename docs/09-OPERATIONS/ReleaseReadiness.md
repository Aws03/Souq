# Release readiness

> **What this page is:** every known blocker between Souq today and a first paying customer, triaged by severity, with the evidence that it is real, what closing it takes, and what proves it closed. It is the page to read before saying "we can go live".
> **How it differs from its neighbours:** [RiskRegister.md](../02-ARCHITECTURE/RiskRegister.md) says *how this system can hurt someone*; [TechnicalDebt.md](../12-ROADMAP/TechnicalDebt.md) says *what we chose to postpone*; this page says **what stops a release**, and tracks each item to closed.
> **Checklist for the release itself:** [ProductionReleaseChecklist.md](ProductionReleaseChecklist.md).

## How this page is built

> **"Phase 17" on this page means the production-hardening engineering mission** (branch `phase/17-production-hardening`), not roadmap Phase 17 (the tenant admin dashboard). `FIXED (Phase 17)` and "found in Phase 17" refer to that mission. Roadmap phases are in [ProductRoadmap.md](../12-ROADMAP/ProductRoadmap.md) §6.

Every item below was **re-verified against the code during Phase 17**, not copied forward. Where the earlier register's description turned out to be incomplete or wrong, this page says so. Items numbered `F-*` were **found in Phase 17** and have no entry in the older registers; `F-7` onward came out of the transaction, concurrency, idempotency and tenant-isolation audits, and each was confirmed by reading the code rather than taken from the audit report.

Numbers are never reused. `F-5` is absent because it was closed, not forgotten.

**Severity**

| | Meaning |
|---|---|
| **P0** | Must be closed before any real customer or real money. Money loss, data loss, a broken deployment, or a legal bar |
| **P1** | Should be closed before the first commercial customer. Correctness or security weakness with a workaround, or an operational gap |
| **P2** | Acceptable to ship with a written limitation |
| **P3** | Future improvement; no release depends on it |

**Status**

`FIXED (Phase 17)` · `OPEN` · `BLOCKED — owner decision` · `BLOCKED — external verification` · `ACCEPTED — documented limitation`

**Evidence** is either *verified in code* (someone read the path and can name it), *reproduced* (a test or a run demonstrates it), or *inherited* (carried from an earlier pass and re-read, but the failure has not been reproduced).

| F-25 | **Two sign-ins for the same account at the same moment: one succeeds, the rest fail with 409 Conflict.** A shopper who double-clicks *Sign in*, or signs in on a phone and a laptop together, gets a conflict error instead of a session | **Found and measured on 2026-09-20 on the running stack, not inferred.** Six concurrent `POST /api/auth/login` for one account returned **one 200 and five 409**; eight concurrent returned **two 200 and six 409**; three sequential logins for the same account returned 200 every time. The cause is that every successful login writes bookkeeping to the **`User` row** — `RecordSuccessfulLogin` clears `FailedLoginCount`, clears `LockoutEndsAt` and sets `LastLoginAt` — and `User` carries a rowversion (`IdentityConfiguration.HasRowVersion`), so the second writer's `WHERE RowVersion = @original` matches nothing. `POST /api/auth/change-password` conflicts the same way and for the same reason (six concurrent with one token: **one 200 and five 409**) | **Fixed by retrying the decision on committed state, with the rowversion left exactly as it was.** `AccountWriter` (Application) wraps the login and change-password handlers in a bounded retry; on conflict `IUserRepository.Reset` detaches the contested `User`, the failed attempt's `RefreshToken`, and its `OutboxMessage`, and the next attempt re-reads. Verification is still recomputed when the hash actually changes, which is what keeps (1) true. **The guard itself is untouched** — no rowversion removed, no isolation level changed, no assertion relaxed. **Re-measured on the running stack after the fix:** 8, 12 and 16 concurrent logins for one account now return **200 every time** (eight used to give 2×200 and 6×409). At **24** simultaneous logins one 409 reappears — that is the documented bound, not a surprise: the budget is sixteen rounds and each round admits one writer. Twenty-four simultaneous writes to a single account is not a person, and a 409 there is a truthful answer. **That bound was re-examined on 2026-09-20 and is not reachable through the shipped configuration.** The `Auth` policy permits 10 requests per 60 seconds partitioned on `{canonical host}|{client address}`, so the limiter answers long before the handler does: 24 simultaneous logins for one account from one client measured **10×200 and 14×429, with no 409 at all** — twice, on the stack with production limits restored. Until then no owner decision is pending on it. The structural way to remove the bound entirely remains moving login telemetry into its own table, which is a schema change and an owner decision rather than a hardening fix | `AuthConcurrencyTests` (integration, real SQL Server, genuinely simultaneous requests): eight concurrent logins for one account over three rounds must **all** return 200 with no 409 and the bookkeeping actually written; eight concurrent change-passwords must yield exactly one 200 with the rest refused *for their real reason* and never 409, the winner's password must be the one that works, and **exactly one** `PasswordChanged` outbox row must exist; a login burst raced against a change-password must produce no 409 and no 5xx, with the old password dead and the new one live afterwards. `AccountWriterTests` pins the mechanism (retry count, reset-per-failed-attempt, no retry on non-concurrency errors, cancellation). `account-password.spec.js` is unchanged — it was left failing rather than adjusted, and now passes | **FIXED — found, reproduced and fixed 2026-09-20** |

| F-13 | A file is written to `IFileStorage` before `SaveChangesAsync`, so a failed save leaves an orphan file | **Found in Phase 17.** Storage leak only — the row never references it. Cleaning orphans is already **FUTURE** in the catalog rules |
| F-14 | **Forward hazard, not a defect today:** the SQL Server provider is registered without a retrying execution strategy. Turning *EnableRetryOnFailure* on later would throw at every explicit `BeginTransactionAsync` unless each of the seven transactional use cases is wrapped in the strategy | **Found in Phase 17.** Deliberately deferred to Phase 23 by [ADR-0021](../11-ADR/0021-transaction-boundaries.md); recorded here because the change breaks them all at once rather than one at a time |
| F-15 | Two `DependencyRuleTests` rules selected entities by matching the namespace string `Souq.Domain.Entities`, so the four entities outside it — `User` and `RefreshToken` in `Souq.Domain.Identity`, `Tenant` and `TenantDomain` in `Souq.Domain.Platform` — were covered by neither. Accounts, sessions and stores could have grown a public setter, or been bound directly by a controller, without failing the build | **Found in Phase 17.** Latent, never violated: there is no public setter anywhere in the Domain (226 are `private set`) and no controller action takes a domain entity. Both rules now select by `IsSubclassOf(Entity)`, the predicate `TenancyRuleTests` already used, taking coverage from 25 entity declarations to 29 while still excluding the Platform *settings* classes, which are not entities. **FIXED (Phase 17)** |

## Not yet assessed

These are named in the mission and not yet re-verified in code; they carry no severity until they are.

- Performance: N+1 queries and unbounded reads on the admin and reporting paths.

**Assessed during Phase 17 and no longer on this list:**

- **Transaction boundaries and concurrency.** No use case splits a logical write across transactions that should be one, and **no transaction spans a network call** — the rule ADR-0021 states is genuinely kept: `CreateOrderHandler` creates the payment intent after its commit, `UpdateOrderStatusCommand` refunds after its commit, and `OrderPaymentConfirmation` confirms before opening one. Every contended aggregate carries a rowversion (Product, Coupon, Order, Payment, InventoryItem, Tenant, User); the four that do not — `CouponRedemption`, `Refund`, `StockReservation`, `Basket` — are covered by their aggregate root's token or, for the basket, deliberately last-writer-wins with checkout re-validating. The open items are F-7 and F-8.
- **Idempotency.** Duplicate Stripe webhooks, duplicate `confirm-payment`, refund retries and coupon reserve/confirm/release are all protected, and the mechanism is worth knowing: the webhook handler **discards the event's payload and type** and re-asks the gateway for the intent's live state, which is what makes both redelivery and out-of-order delivery safe without a processed-events table. Order creation (F-8) is the one unprotected entry point.
- **Tenant isolation.** Audited across all 13 modules against the controllers rather than the generated inventory: no cross-tenant or cross-customer path was found. Every mechanism ADR-0022 claims was confirmed present and applied by reflection across the model, and `TenantIsolationTests` enumerates the live endpoint list so the matrix cannot silently drift. The residual items are F-1 and F-2, both already recorded.

## M15 — the dedicated security review, finding by finding

M15's exit criterion is the roadmap's own: **every finding is either fixed with a test, or accepted here with a written
rationale.** The review ran STRIDE across all thirteen modules, the ASVS Level 2 checklist, the authorization matrix
against its own documentation, cross-tenant coverage against the generated endpoint inventory, and the headers, rate
limits, secrets and dependency audit against the running container stack. Nothing below is inferred from a document; each
was traced to code, and the exploitable ones were reproduced before being fixed.

### Fixed, with a test that fails against the old behaviour

| Finding | Why it mattered | Closed by |
|---|---|---|
| **The rate limit could be bypassed by changing the host's letter case.** Proven on a running stack: ten logins then 429, then fourteen more varying only capitalisation, all accepted | Unlimited credential stuffing, reset-mail flooding, coupon guessing and account creation — everything the limiter exists for. No proxy bypass, no forged header; it worked straight through nginx | One `RequestHost.Canonical` shared by the limiter and tenant resolution; `AuthSessionTests` covers upper, mixed and trailing-dot |
| **Approved reviews leaked for products withdrawn from the storefront** | An anonymous caller could tell a withdrawn product from one that never existed, and read its reviews and rating distribution | The same visibility predicate the catalogue uses; `ReviewModerationTests` |
| **Reading customer PII was not audited while exporting it was** | Worse than auditing neither: the list carries name, email and phone, 100 to a page, so paging it harvests what the export does — and the trail said nobody exported anything | `ListCustomersQuery` and `GetCustomerQuery` are `IAuditable`, the list recording its filter and page |
| **The payment webhook read an unbounded body before verifying anything** | Anonymous, unrate-limited, and the store key was AES-GCM-decrypted and an HMAC computed over whatever arrived, before the signature was judged | `[RequestSizeLimit(64 KB)]` — real events are orders of magnitude under it |
| **Checkout accepted an unbounded line quantity** | `CheckoutQuote` prefers an explicit `items` array over the basket, so it skipped all three of the basket's guards; two huge quantities for one variant also overflow their checked sum into a 500 per request | The basket's own ceiling in the validator; `CreateOrderHandlerTests` |
| **No API response forbade caching** | `GET /api/account/export` returns a customer's whole profile, addresses, orders and reviews as a download, and previously said nothing about caching | `Cache-Control: no-store` as a **default, not a mandate** — the storefront config keeps its deliberate `no-cache` + ETag |
| **A sibling host under a merchant's domain could plant a session** | Souq is white-label and merchants bring their own domains; `SameSite` governs *sending* and says nothing about a same-site host *setting* a cookie. The storefront would refresh straight into the attacker's session | `__Host-` prefix on both cookies, suspended when not Secure so development still works |
| **Nobody was told when their password changed** (ASVS 2.2.3) | A mailbox takeover resets the password and signs out every session, and the owner sees only an unexplained lockout | `PasswordChanged` outbox message; its button goes to recovery, because a reader who did not do it needs a way to act |
| **Password-reset mail had no per-account throttle** | The source comment named the API rate limit as its defence, but that partitions on the *caller* — it guards the server, not the mailbox. Burying the message someone needs, and burning the store's sender reputation for all its customers | A two-minute cooldown derived from the existing token expiry, at enqueue only (see the note in `IdentityEmailHandlers` for why not at dispatch) |
| **M13's search-log retention did not hold under load** | One batch per six hours against an anonymous, unrate-limited writer: the documented ninety days were not enforced at all | The purge repeats until a batch comes back short, with a per-cycle ceiling |
| **A rejected image upload left the file on disk** | `IFileStorage` has no delete, so every attempt at a full gallery orphaned a file | `Product.HasRoomForImage`, asked before the write |
| **Failed sign-ins produced no security log, and no log carried a source address** | A credential-stuffing run was indistinguishable from users with bad memories: no account, no source, nothing to aggregate or alert on | Outcome-tagged warnings in `LoginHandler` (never the address) and `ClientIp` in every log scope |
| **A two-hop proxy chain silently collapses every client to the terminator's address** | `ForwardLimit` defaults to 1 while `Deployment.md` recommends terminating TLS in front of nginx, which *appends* to `X-Forwarded-For`. One shared rate-limit bucket, and an audit trail naming the edge | Configurable, and — more importantly — `ProxyTrustDiagnostics` now detects and reports it |
| **The validation pipeline fails open** | 59 of 141 requests had no validator and nothing in CI required one, in a repository that build-enforces everything else | `ValidationRuleTests`: anything carrying free-form input needs a validator or a written exemption naming its actual guard |

### Accepted, with the rationale written down

| Finding | Why it is accepted |

| **SQL Server Row-Level Security is not adopted** | [ADR-0043](../11-ADR/0043-row-level-security-evaluation.md). Every path around the application filter is already a failing build; RLS's per-connection session value is a silent footgun under EF pooling; the platform area needs a mode switch and four exemptions, which is a second copy of the same rules; and the application connects as `sa`, which could disable the policy anyway. The three conditions that void this are listed in the ADR |
| **The audit row and the change it describes commit separately for three platform→tenant commands** | TD-55, and SEC-LOG-09 corrected from CURRENT to PARTIAL. Not attacker-triggerable; fixing it means deciding how a Platform-area row crosses the tenant write guard, which is a design task rather than a move |
| **`orders.manage` can move money by cancelling a paid order** | R-03, unchanged and deliberate, pinned by a test that asserts the refund happens. M15 added it to the role table in `AuthenticationAndAuthorization.md`, which is the page a reader consults and did not say so |
| **The SPA's CSP is still Report-Only** | R-16. M15 gave it the browser pass its own nginx comment asks for: **zero violations across sixteen routes** (storefront, search, product, cart, account, all ten admin screens), in both light and dark and in both languages, collected from the browser's own `securitypolicyviolation` events. It is *not* flipped to enforcing, because the one path that cannot be exercised without a real Stripe key is checkout — and that is precisely where the comment warns a wrong policy breaks a store silently. Enforcing it needs one pass against a real payment configuration, which is a production-only action |
| **`ForwardedHeaders` trusts the whole Docker bridge range while compose publishes the API on 5201** | R-11 / G-17, already a REQUIRED item in `ProductionReleaseChecklist.md`. Deployment-shaped, so it belongs to M17 |
| **`TrustServerCertificate=True` on the application↔database connection** | Encrypted but unauthenticated. Deployment configuration, not application code, and it travels with the least-privilege-login work (G-09) that is already scripted and not yet applied. Recorded here because the catalogue framed `sa` purely as a privilege problem and never mentioned the certificate |
| **SMTP can fall back to cleartext if an operator sets a non-465 port with `EnableSsl=false`** | Configuration-shaped. Recorded as a gap; the fix that matches this codebase's own style is a startup warning, which belongs with the other provider warnings rather than in a security review's last hour |
| **No MFA, no breached-password check, 8-character minimum** | Pre-existing, documented (G-15, SEC-AUTHN-02), and product decisions rather than defects |

### The twenty-one questions, answered

1. **Can the database be recovered?** Yes — and its freshness, integrity and drill age are now checkable by a command.
2. **Has restoration actually been rehearsed?** Yes, with the source stack destroyed first. The rehearsal writes `LAST-RESTORE-DRILL`, so "when did we last prove it?" is answerable without asking anyone.
3. **Can the runtime app operate without `sa`?** Yes, measured. And a deployment that ignores it now **says so at every boot**, naming the roles the identity holds.
4. **Is production HTTPS/proxy behaviour safe?** The behaviour is correct and the commonest misconfiguration is now detected at runtime. **TLS itself is still not provided.**
5. **Are health checks usable?** Yes, with a documented contract drilled on a running stack: database down → 503 while liveness stays 200, self-healing in ~11 s with zero restarts.
6. **Does CI enforce meaningful quality?** The checks are meaningful and were verified step by step — one caught a real tracked credential. It **enforces** nothing until branch protection is on.
7. **Can a new engineer deploy from repository documentation?** Yes; a clean deploy from no images and no volumes reached healthy in 95 s.
8. **Is rollback understood and safe?** Understood, measured, and a new destructive migration now fails the build until recorded.
9. **Can demo data enter production accidentally?** No — proven on a production-shaped database, and `audit-config.sh` refuses `SEED_DEMO_DATA=true` for production.
10. **Are secrets and sensitive logs protected?** Yes, and the secret scan proved its worth by finding a literal password in a tracked script.
11. **Has F-17 been measured?** Yes; accepted for launch with a recorded trigger.
12. **Has F-7 been classified/resolved?** Resolved.
13. **Has F-8 been classified/resolved?** Measured and designed; **awaiting one owner decision**.
14. **What remains external?** P-05 only.
15. **What remains owner/business/legal?** P-03, P-06, D-13, R-03, F-8, branch protection, and the backup schedule/retention.
16. **What remains purely product functionality?** From roadmap Phases 16–18: the storefront preview (D-22) and platform-wide settings (P-07) in Phase 18 🟡, both waiting on owner decisions. Phase 17 is ✅. Phases 19–23 follow.
17. **Is Souq technically ready for a first deployment?** **Yes, conditionally** — TLS terminated, least-privilege logins applied, backup scheduled. All three are deployment actions with tested mechanisms, and two of the three now announce themselves if skipped.
18. **Is Souq commercially ready for the first paying customer?** **No.**
19. **If not, exactly what prevents it?** The licence (P-03), tax (P-06), the JOD verification (P-05), and the three deployment actions above.
20. **What is the next engineering mission?** None is required before a deployment. What remains in this repository is **product work**; everything operational left is a deployment or owner action, each named above.
21. **What is the next product roadmap capability?** Phases 16 and 17 are delivered (Phase 16 closed with the variant picker, [ADR-0041](../11-ADR/0041-storefront-variant-selection.md)); in Phase 18, D-22 and P-07 need the owner first. After them, **Phase 19 — Testing** ([ProductRoadmap.md](../12-ROADMAP/ProductRoadmap.md) §6).

## How to use this page

1. **Before a release:** everything in P0 is either `FIXED` or has a deliberate, written acceptance from the owner. No exceptions — P0 is defined as "money, data, deployment or law".
2. **Before the first commercial customer:** work down P1. Items marked *owner decision* cannot be closed by engineering alone; take them to the owner as a batch.
3. **When an item closes:** move it to `FIXED` with the commit, and delete its row from [RiskRegister.md](../02-ARCHITECTURE/RiskRegister.md) and its entry in [TechnicalDebt.md](../12-ROADMAP/TechnicalDebt.md) in the same change. This page keeps the history; those two keep only what is still true.
