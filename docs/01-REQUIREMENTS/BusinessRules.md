# Business rules

This page is the inventory of the rules the Souq system **actually enforces today**, extracted from the code, each one traced to the place that enforces it and the test that proves it. It is not a wish list: a rule is here only if code refuses something, or allows it, because of it.

A *business rule* here means one of four things:

1. **An invariant an entity guards itself** — the state cannot become invalid, because the only door into it refuses (`Order.Place`, `Money`'s constructor). Violations raise a `DomainException` and reach the client as `422` with a stable `code` (ADR-0017).
2. **A rule that needs a lookup**, so it lives in an Application handler: uniqueness, ownership, eligibility, limits (`CreateReviewHandler`'s "you must have received the product").
3. **A security or tenancy rule**: who may call a use case, whose rows they may see, which store a request belongs to.
4. **A rule the database also enforces**, as the last guard against races: unique indexes, check constraints, `rowversion`.

## How to read the tables

| Column | Meaning |
|---|---|
| ID | Stable reference (`BR-ORD-09`). Cite it in code review, tests and ADRs. |
| Rule | The rule in business language. |
| Meaning / why | What it protects, and why the system was built this way. |
| Module | The module that owns the rule ([Modules.md](../04-MODULES/Modules.md)). |
| Enforcement | The symbols that enforce it; the database constraint is named when the database enforces it too. |
| Tests | The test classes that prove it. |
| Notes | Gaps, single-layer enforcement, open decisions. |

Test abbreviations: **D** = `tests/Souq.Domain.Tests` · **A** = `tests/Souq.Application.Tests` · **I** = `tests/Souq.IntegrationTests` · **AR** = `tests/Souq.ArchitectureTests` · **FE** = frontend Vitest under `frontend/src`. Many test method names are Arabic; they are quoted as they are.

Labels: unlabelled statements are current behaviour. **UNTESTED** = no test found that proves this rule. **PLANNED** = scheduled in [ProductRoadmap.md](../12-ROADMAP/ProductRoadmap.md). **DEFERRED** / **FUTURE** = not scheduled. **Frontend only** / **Convention only** = enforced in one place that a server-side caller can bypass.

## How to add a rule

1. **Domain first.** If the rule can be decided from the data inside one aggregate, it belongs in the entity, behind the method that changes state, and it throws a `DomainException` with a stable code. If it needs a lookup (uniqueness, another aggregate, the current user), it belongs in the Application handler and returns an `Error` with a code. Never put it in a controller: `DependencyRuleTests` fails the build if you do.
2. **A test.** Domain rules get a `tests/Souq.Domain.Tests` case; lookup rules get a handler test with doubles; rules that only the database can guarantee (races, uniqueness) get an integration test.
3. **Then this page.** Add the row, with the enforcement path and the test. A new domain exception type also needs a row in `DomainExceptionCodeTests`, which fails until you add it.

## 1. Tenancy and platform

One API and one database serve every store. Every rule below exists so that a bug cannot turn into "store A saw store B's data".

### Rules enforced in one layer where two would be expected

- **Module flags for Reviews and Wishlist** (BR-TEN-20) are enforced only by the endpoint attribute. Coupons are the only module also checked inside a use case (BR-CPN-11). A future internal caller of `CreateReviewHandler` or `AddToWishlistHandler` would bypass the flag.
- **The default-language text requirement** (BR-CAT-07) lives only in the handlers; `Product` and `Category` accept any supported set. Changing a store's default language later leaves existing products without a name in the new default, and nothing backfills them: `CatalogTranslation.NameIn` then falls back to Arabic, then to the first language.
- **Blocked customers** (BR-CUS-06) are stopped at ordering and reviewing only. They can still fill a basket and a wishlist; nothing there checks `Customer.IsBlocked`.
- **Coupon fixed amounts** (BR-CPN-02) are a raw `decimal`, so unlike every other money input they are never checked against the currency's minor units. `CalculateDiscount` rounds the result, so the visible effect is limited to an over-precise stored value.
- **A coupon's fixed discount carries no currency at all.** `Coupon.Value` is a bare `decimal` serving two meanings (a percentage *or* an amount), and `CalculateDiscount` stamps the basket's currency onto it — so "5 off" created under one currency would become "5 off" in another. `MinOrderAmount` *is* a `Money` with its own column, so the coupon row stores a currency for its threshold but not for its discount. Phase 17 closed the way in (BR-TEN-18 now counts coupons, and `EnsureUsable` compares currencies) rather than the asymmetry itself: giving `Value` a currency is a schema change (R-09).
- **Category parent** (BR-CAT-13): the parent foreign key is single-column, so only the handler lookup and the query filter keep a parent inside the store — every other reference between store rows is a composite key the database enforces.
- **The password policy** (BR-IAM-05) exists only in the Application validator; the Domain deliberately sees hashes only.
- **Frontend-only rules:** the visitor language fallback (BR-STO-15) and the Arabic-comma country parsing in the shipping form (BR-SHP-03). Mirrors that exist on both sides — basket quantity cap, wishlist cap, refund amount guard, category descendant exclusion — are safe because the server repeats them.

### Rules whose owner is ambiguous

- **The verified-buyer rule** (BR-REV-01) is owned by Reviews but reads Ordering's `IOrderRepository` directly, and `CreateReviewHandler` also reads `ITenantRepository` (Platform). Module contract tests only cover `Features/*/Contracts`, so a handler reaching into another module's **domain** repository is invisible to them. The same pattern appears in `CreateOrderHandler` (Customers' `ICustomerRepository` and `Customer`), `PricingService` (Promotions' `ICouponRepository` and `ICouponRedemptionRepository`, Catalog's `IProductRepository`), `CustomerErasure` (Identity's `IUserRepository` and refresh tokens, Shopping's basket and wishlist), `UpdateMyProfileHandler` (renames the Identity `User`) and the notification handlers (orders, customers, users, products).
- **Review publication policy** (BR-REV-05) is a Reviews rule stored on the Platform aggregate (`Tenant.ReviewsAutoApprove`) and edited through a store-settings permission, while moderation uses a Reviews permission.
- **The audit trail** (BR-TEN-23 to BR-TEN-25) has no owning module: the entity is in the shared kernel, the behaviour is in Application common, and only reading it belongs to Platform.
- **Checkout expiry** (BR-ORD-27) is orchestrated by Ordering, triggered by an Inventory hosted service, and timed by an Inventory setting.
- **The full refund on a cancelled paid order** (BR-ORD-20) is decided by Ordering and executed by Payments; whether that should ever be automatic is part of open decision **D-13**.
